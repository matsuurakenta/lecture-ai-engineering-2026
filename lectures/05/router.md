# 質問に応じて検索方式を選ぶルーター

既存ファイル・関数・検索データは変更せず、`app/router.py`から既存の
`search_materials`、`browse_tree`、`search_graph`を呼ぶ。

## 実行

```bash
uv run python -m app.router --trace 'LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？'
uv run python -m app.router --trace '第3回では何をどのような順に説明していますか？'
uv run python -m app.router --trace '第3回のコンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか？'
```

同じ質問を`uv run python -m app.agent --trace '質問'`でも実行して比較する。
両方式は同じ`AIE_MODEL`と第1〜3回・214ページを使う。

## データ構造と検索方法

1. 回答と同じモデルで質問を解釈し、構造化出力`RouteDecision(method, reason)`を得る。
2. `method`に応じた取得方針と、必要時に追加検索できる既存ツールを回答モデルに渡す。
3. 取得した本文を根拠として回答する。資料に答えがなければ確認できないと伝える。

| method | 想定する質問 | 最初に使う方法 | 根拠不足時の方法 |
|---|---|---|---|
| vector | 特定の事実・定義・仕組み | ベクトル検索 | 検索語変更、Graph |
| tree | 講義・章の構成、順序、概要 | Treeの目次→ページ全文 | ベクトル検索 |
| graph | 複数ページの関係・条件・例 | Graph | ベクトル検索、Tree |
| hybrid | 複数種類の要求、分類が曖昧 | ベクトル検索 | Tree・Graph |

方式の選択と追加検索の必要性はモデルの判断であり、正解や取得順序を保証しない。
「比較」という語だけでGraphにせず、LoRA/QLoRAのように単一ページで説明できそうなら
vectorを選ぶよう指示している。対象の回が指定されただけではTreeにしない。

Treeは既存の講義→章→ページの階層を利用する。Graphは既存のページ・用語ノードと
`next_page`・`mentions`を利用し、ベクトル検索の入口から最大2 hop、最大10ページを取得する。
検索結果はツール経由で回答モデルに渡す。追加の索引構築や埋め込みは不要。

分類と回答の使用量を共有し、`--trace`の時間・トークン・応答回数・推定費用には
分類の分も含める。既存方式と同じく埋め込み・索引構築の費用は含まない。
モデル応答は合計16回、ツールは20回で停止する。上限はCLI引数で変更できる。

## 比較で残す情報

- 単一ページ、複数ページ、章全体、複合要求、資料にない質問を用意する。
- 質問ごとの`[route]`と選択理由、実際のツール名・引数・回数を記録する。
- 必要な根拠ページが取得できたか、取得した本文を回答に使えたかを分けて見る。
- 正しさ・引用・回答保留の適切さと、時間・トークン・費用を比較する。
- 分類が適切でも検索が失敗する場合、分類が誤っても追加検索で回復する場合を記録する。

実測結果は利用者が実行したログから記入する。分類の追加コストや誤分類があるため、
基本RAGより改善するとは事前に断定できない。
